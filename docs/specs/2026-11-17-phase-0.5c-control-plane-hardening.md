## 1. 目标

0.5-A / 0.5-B 已经证明「能接管」；0.5-C 要证明「能长期跑」。本期把控制面从演示级提升到可承载 Phase 1 Web 控制台的稳定服务，验收看四条硬指标：

1. **重启不丢**：杀 daemon 再启动，未完成会话仍可见、可读、可接管。
2. **重复不双写**：同一 dispatch 重复 3 次只产生 1 个会话；同一会话的并发写操作串行落库。
3. **崩溃不锁死**：adapter 或 daemon 崩了，租约在 TTL 内释放，子进程不残留。
4. **契约能冻结**：`/api/cp` 与 WS 事件 schema 定稿成 v1，前端只依赖这份契约即可开发。

## 5. 数据模型（schema v4）

`SCHEMA_VERSION` 由 3 升到 4；`migrate()` 在 `current < 4` 时只做加法，不重建表：

~~~sql
CREATE TABLE IF NOT EXISTS instances (
  instance_id TEXT PRIMARY KEY,
  pid         INTEGER NOT NULL,
  host        TEXT NOT NULL,
  version     TEXT NOT NULL,
  started_at  TEXT NOT NULL,
  heartbeat_at TEXT NOT NULL,
  ended_at    TEXT
);

ALTER TABLE leases ADD COLUMN instance_id TEXT NOT NULL DEFAULT '';
CREATE INDEX IF NOT EXISTS idx_leases_instance ON leases(instance_id);

ALTER TABLE sessions ADD COLUMN dispatch_key TEXT;
CREATE UNIQUE INDEX IF NOT EXISTS idx_sessions_dispatch
  ON sessions(dispatch_key) WHERE dispatch_key IS NOT NULL;

ALTER TABLE checkpoints ADD COLUMN version INTEGER NOT NULL DEFAULT 1;

CREATE TABLE IF NOT EXISTS audit_log (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  ts          TEXT NOT NULL,
  instance_id TEXT NOT NULL,
  actor       TEXT NOT NULL,
  action      TEXT NOT NULL,
  session_key TEXT,
  outcome     TEXT NOT NULL,
  error_code  TEXT,
  detail_json TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_audit_session_ts ON audit_log(session_key, ts);
CREATE INDEX IF NOT EXISTS idx_audit_ts ON audit_log(ts);
~~~

约束：

1. 旧库升级只执行一次 ALTER；新建库按 v1→v4 顺序建表，结果同构。
2. `leases.instance_id` 对历史行为空串；启动清扫把空串视为「历史租约」删除。例外：未过期的 `driver='human'` handoff 租约先改归属到当前实例（保留），其余非当前实例的租约全部删除。
3. `sessions.dispatch_key` 只由 dispatch 创建会话时写入；发现/登记路径保持 NULL。
4. `audit_log` 只追加不更新；保留策略见 §7.4。
5. 内存对象同步扩字段：`Lease.instanceId`、`Checkpoint.version`（additive，不改既有字段语义）。
6. **迁移策略 expand-only（只加不删、不改列语义）。** 旧列保留到 Phase 1 之后再收缩；升级前把库文件复制到 `<dataDir>/db-backup/pi-workbench-v<旧版本>-<timestamp>.db`，保留最近 2 份。

### 6.2 新增端点

- `GET /api/cp/version` → `{ api: "1", schemaVersion: 4, daemon: WORKBENCH_VERSION, instanceId: string }`。
- `GET /api/cp/audit?sessionKey=&since=&limit=` → `{ items: AuditEntry[] }`，按 id 升序，默认 limit 100、上限 1000。
- `GET /api/cp/assets` → `{ mcpServers: McpServerEntry[], skills: SkillEntry[], memory: { projection: "disabled" } }`。
- `GET /health` 增补 `instanceId`、`uptimeMs`、`db: { schemaVersion, ok }`、`adapters: { agent, available }[]`（全部 additive，保留 `ok` / `pid` / `version`）。

### 6.3 不变式

1. `/api/cp/*` 全部要求 `Authorization: Bearer <token>`；`/health` 例外。
2. 错误响应保持 `{ error: { code, message, details } }`。
3. WS 事件保持 `{ seq, sessionKey, type, source, ts, payload, idempotencyKey }`。
4. v1 内只允许新增可选字段与新端点；删字段、改语义一律走 `/api/cp/v2`。
5. `GET /api/cp/version` 的 `api` 与 `schemaVersion` 必须与契约测试里的常量一致。

## 7. 行为规范

### 7.1 C01 重启恢复

**启动顺序（硬约束，失败即退出并释放实例锁）：**

1. 抢实例锁 `workbench.pid`；
2. 开库 + `migrate()` 到 v4；
3. 写 `instances` 一行（`instance_id` = `randomUUID()`，`pid`，`host`，`version`，`started_at`）；
4. **租约清扫**：先把未过期的 `driver='human'` 租约改归属到当前实例（handoff 需要跨重启保留），再删除其余 `instance_id != 当前` 的租约（单实例锁保证其他实例已死），随后给 `leases.instance_id` 补写当前值；
5. `registry.loadFromDb()` 恢复会话；
6. `reconcileSessions()` 对账（见下表）；
7. 起 HTTP/WS，后台跑 Agent 探测；
8. 把上一个实例的 `ended_at` 补齐。

**对账规则：**

| 会话 driver | 重启后 driver | 重启后 status | 附加动作 |
|---|---|---|---|
| `pi` / `claude` / `codex`（注册表里就是这三个值之一） | `none` | `unknown` | 追加一条 `state_update` 事件，payload `{ reason: "daemon_restart", previous: { driver, status } }` |
| `human` | `human` | 保持 `handoff` | 租约仅在未过期时保留；过期则按无租约处理 |
| `none` | `none` | 保持原值 | 不补事件 |

> 说明：`Driver` 类型只有 `pi` / `human` / `none` 三值，`agent` 才是 `claude` / `codex` / `pi`。对账按 `driver` 判定，不按 `agent`。
>
> 依据：A2A 把 `TASK_STATE_UNSPECIFIED` 定义为「unknown or indeterminate」的合法状态；ACP 要求显式 `session/resume`，已丢弃的会话返回 -32002。控制面照此办：重启后不按 transcript 猜状态，等显式 attach。

**接管路径：** 重启后 `GET /sessions/:key/transcript` 仍可读（读文件，不需要 driver）；要写或续聊，先 `POST /sessions/:key/attach`（3s 超时）把 driver 接回来，成功后 status 置 `idle`。attach 失败返回 `E_RESUME_REJECTED` 或 `E_AGENT_UNAVAILABLE`，不改会话状态。

**验收：** 杀 daemon（`Stop-Process -Force`）→ 重启 → `GET /sessions` 条数不变、transcript 可读、attach 后可 inject；证据写 `docs/evidence/phase-0.5c/restart.md`。

### 7.2 C02 幂等与并发

**dispatch 状态机（`dispatches` 表）：**

| 记录状态 | hash 相同 | 行为 |
|---|---|---|
| `done` | 是 | 直接返回 `session_key` 对应 SessionRef（200） |
| `done` | 否 | `E_IDEMPOTENCY_CONFLICT`（409） |
| `failed` | 是 | 允许重试：`UPDATE ... SET status='reserved'` 后重新执行 |
| `reserved`，年龄 < `dispatchReservedTtlMs`（默认 120s） | 是 | `E_DISPATCH_IN_PROGRESS`（409，替换现在的 `E_ADAPTER_DOWN`） |
| `reserved`，年龄 ≥ TTL | 是 | **回收**：见下 |

> TTL 语义参照 Kubernetes Lease：`leaseDurationSeconds` 以最后一次 `renewTime` 起算，只有持有者不续约才过期。我们同样以 `updated_at` 为准，长任务用心跳续约。幂等键记录本身保留 24h（与 Stripe 一致），TTL 只约束「预留窗口」。

**回收算法（必须原子）：**

1. 先按 `sessions.dispatch_key = idempotencyKey` 查会话；命中说明上次其实已经建好会话，直接 `complete` 并返回该 SessionRef。
2. 未命中，执行 `UPDATE dispatches SET status='reserved', created_at=?, updated_at=? WHERE idempotency_key=? AND status='reserved' AND updated_at <= ?`；`changes=1` 才继续，否则回到轮询。
3. 只有赢家允许调用 `newSession`；新会话写入 `dispatch_key`。

**写操作串行化：** 新增 `SessionWriteQueue`，按 `sessionKey` 排队；`inject` / `interrupt` / `checkpoint` / `handoff` / `handback` 全部经队列执行。队列上限 32，等待超时 30s → `E_SESSION_BUSY`（429）。队列只保证单进程内 FIFO；跨进程仍靠租约。

**验收：** 同一 `idempotencyKey` 并发 3 次只产生 1 个会话、3 个响应 SessionRef 相同；10 个并发 inject 的事件 seq 严格递增且无交错；证据写 `docs/evidence/phase-0.5c/idempotency.md`。

### 7.3 C03 checkpoint / handoff 硬化

**检查点文件格式（v1，Markdown + front matter）：**

~~~markdown
---
pi-workbench-checkpoint: 1
session: claude:<nativeId>
created: 2026-11-17T01:00:00.000Z
cursor: "12345"
agent: claude
---

# 检查点

## 摘要
<summary>

## 触碰文件
- <path>

## 下一步
<nextStep>
~~~

- 写入方式：先写 `<path>.tmp`，`renameSync` 原子替换；失败不留半文件。
- 数据库 `checkpoints.version` 固定写 1；读取缺列时按 1 处理。
- `Checkpoint` 接口新增 `version: number`（additive）。

**审计：** 每次 `handoff` / `handback` / `checkpoint` 的每一步都写 `audit_log`（`action`、`session_key`、`actor`、`outcome`、`detail_json` 含 step、耗时、错误码）。审计写失败只记 stderr，不阻断主流程。

**失败补偿：**

| 失败步骤 | 会话状态 | 租约 | 返回 |
|---|---|---|---|
| quiesce（cancel 失败） | 不变 | 归还调用方 | 503 + `E_HANDOFF_FAILED`，detail.step=cancel |
| checkpoint 写失败 | 不变 | 归还调用方 | 500 + `E_CHECKPOINT_FAILED` |
| close 失败 | 回滚为原状态 | 归还调用方 | 503 + `E_HANDOFF_FAILED`，detail.step=close |
| handoff 命令拼接失败 | `exited` | 释放 | 503 + `E_HANDOFF_FAILED`，detail 带 checkpointPath |
| handback resume 被拒 | 保持 `handoff` | 保持 human | 409 + `E_RESUME_REJECTED` |

**两次往返：** 同一会话连续两次 handoff → human → handback 后，第三次 checkpoint 的 cursor 必须大于第一次，且 transcript 能读到人类回合的消息。

### 7.4 C04 错误与进程治理

- **子进程登记：** 所有 adapter / RPC 子进程进 `ProcessRegistry`；退出时标记 `exited`，对该 driver 名下 `running` 会话发 `error` 事件（`E_ADAPTER_CRASHED`），释放该 driver 持有的租约，status 置 `exited`。
- **优雅退出：** SIGINT / SIGTERM / SIGBREAK → 停止接新请求 → 关 WS → `pipeline.dispose()` → 子进程树 kill → 释放实例锁 → 退出；全程上限 5s，超时强退。
- **日志轮转：** 默认 `~/.pi-workbench/logs/daemon.log`，单文件 10 MB、保留 5 份；`PI_WORKBENCH_LOG_DIR` 可覆盖。
- **健康检查：** `/health` 返回 §6.2 字段；db 打不开时 `ok: false` 且 503。
- **审计保留：** 启动时删除 `audit_log` 中超过 30 天的行（可配置 `auditRetentionDays`）。

### 7.5 C05 资产桥最小版（只读清单，保留）

## 12. 风险与回退

- **重启恢复的假象**：原生进程已死，attach/resume 会被 ACP 拒绝。处理：只承诺「会话记录与 transcript 不丢」，不承诺「原生进程能复活」；失败返回结构化错误。
- **回收导致双会话**：靠 `sessions.dispatch_key` 唯一索引兜底；回收前必查。
- **单实例假设**：实例锁在 Windows 上依赖 pid 存活判断；跨用户/容器不保证。文档写明限制。
- **C05 拖慢主线**：默认只读清单，任何同步能力留到 Phase 3。
