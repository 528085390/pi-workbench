## 2. 本轮新发现

### R1（P0，必修）codex 的 inject / interrupt / handback 通过 HTTP 必然失败

`index.ts:303-317` 注入的守卫：

```ts
const lease = leases.current(ref.key);
if (lease !== null && lease.clientId !== PI_AGENT_CLIENT_ID) {   // PI_AGENT_CLIENT_ID = "pi"
  throw new WorkbenchError("E_LEASE_CONFLICT", …);
}
```

而真实调用方的 clientId 是 `pi:<pid>`（`extension/src/index.ts:282`），`takeover.#driverWrite` 只对 `agent === "pi"` 做租约换名（`takeover.ts:542`），codex 不在其中。于是：

1. `POST /sessions/:key/inject`（clientId = `pi:<pid>`）→ `assertWriter` 通过 → `driver.inject` → 守卫发现持有人 `pi:<pid>` ≠ `"pi"` → **409 E_LEASE_CONFLICT**；
2. `POST /sessions/:key/interrupt` 同理；
3. `handback`：租约是 `handoff-<id>` → `driver.resume` 被拦 → `takeover.handback` 的 catch 把它包成 **E_RESUME_REJECTED**（错误码还错位了）。

**已实测复现**（临时脚本，复刻 `index.ts` 的注入 + `takeover` 的调用顺序，用完已删）：

```text
RESULT inject: THROW E_LEASE_CONFLICT — 租约被其他客户端持有：pi:4242
RESULT resume(handback): THROW E_LEASE_CONFLICT — 租约被其他客户端持有：handoff-pi:4242
adapter calls: []          ← 连 adapter 都没起来，任何 ACP 请求都没发
```

为什么 341 个测试还是全绿：没有任何用例覆盖「codex 会话 + 合法 clientId 持租约 + HTTP inject/interrupt/handback」。E2E 的 codex 写操作全在 driver 级（`codex` 阶段 L49–L53，脚本自己 new 实例、不注入守卫），HTTP 只跑了 dispatch / see / handoff（handoff 和 close 在守卫里被豁免，所以碰巧通过）。

最小修法（任一）：
- **A（推荐）**：让 `takeover.#driverWrite` 对**所有 driver** 做租约换名，而不是只对 pi —— 守卫读到的就是引擎自己的身份，语义自洽；或
- **B**：删掉 driver 级身份守卫，只保留 `TakeoverEngine.assertWriter`（0.5-A 的唯一真相就没变过），把 S6 记作「不采纳，理由是引擎已兜底 + driver 看不到调用方身份」；或
- **C**：把「acting clientId」作为参数穿到 driver 的写方法里，守卫检查 `lease.clientId === actingClientId`。

无论选哪个，请补 3 条用例：`codex + pi:<pid> 持租约 → inject 200`、`→ interrupt 200`、`handoff 后 handback 200`。这也是本轮最该补的测试缺口。

### R2（P1）发现 / 登记路由覆盖活跃会话的实时状态

`server.ts:354` 与 `server.ts:400` 都用 `registry.upsert(...)`，而 `SessionRegistry.upsert`（`registry.ts:82-100`）对同 key 是**整行覆盖**（status / driver / transcript_path / caps 全换）。

而 discovery 产出的 ref 是 `status:"unknown"`、`driver:"none"`，路由还把 status 强写成 `"idle"`。于是对一个**正在被 daemon 驱动**的会话再调一次 `GET /sessions/discover`（或 `POST /sessions`），会把它打成 `idle` + `driver:"none"`：

- `takeover.handoff` 的第 2 步以 `ref.status === "running"` 判断是否 quiesce → 被覆盖后**跳过 cancel**，直接把正在跑的会话交给原生终端 —— 正是 M1 刚堵上的双写口子；
- `/sessions` 里 `driver` 显示 `none`，UI/LLM 会误判控制权；
- 若该会话的 `transcriptPath` 被解析层补写过，也可能被覆盖回旧值。

建议：discovery 登记改为「不存在才插入，存在只补 transcriptPath（且不覆盖 status/driver）」，或给 `upsert` 加一个 `mode: "insert-if-absent" | "merge"` 参数；`POST /sessions` 对已存在 key 返回 409 或做同样合并。

### R3（P2）`notice` 只加到了消息模型，没加进事件管线映射

- `packages/shared/src/index.ts:26` 给 `UnifiedKind` 加了 `"notice"`；
- `pipeline.ts:58-63` 的 `TRANSCRIPT_KIND_TO_TYPE` 没有 `notice` → `ingestTranscript` 会走「未知 transcript kind=notice，已丢弃」分支（`pipeline.ts:144-147`）；
- `transcript/claude.ts` 没实现同样的 notice，三解析器在这一点上又不一致。

要么把 `notice → "notice"`（`SessionEventType` 已有该值）加进映射表，要么明确注释「notice 只面向 transcript 消费者，不进事件流」，并给 claude 解析器补同款行为。

另外 notice 是作为**消息**塞进返回页的（`transcript/{codex,pi}.ts`），会占 `limit` 名额、也会被算进 `unread`。spec §10.4 原文是「发 notice 事件」，两种解读都说得通，但至少要在注释里写清「这是消息不是事件」，否则后续会有人当 bug 修。

### R4（P2）新增行为缺测试 + 缓存没人清

- `codex-driver.ts:322-336` 的 adapter 重建（S5）没有单测：仓库里 `isAlive` 只出现在 `test/cli.test.ts`（那是 CLI 的进程探测），fake adapter 也没实现 `isAlive` 分支。建议补「`isAlive()` 返回 false → 重建并退订旧 adapter」。
- `discover/codex.ts:42` 的 `clearCodexDiscoveryCache()` 导出后**没有任何调用点**（含测试）。两个缓存还是模块级、无上限、无淘汰：长跑 daemon 里已删除的 rollout 条目永远不会释放。建议测试里在 `beforeEach` 清一次，并考虑按 mtime 做 LRU 或加条数上限。
- `POST /sessions`（`server.ts:377`）只做了必填校验，没有校验 `cwd` / `transcriptPath` 是否存在、也没有幂等语义，测试只有 discover 那两条；这条路由会写进注册表，建议至少补「同 key 重复 POST 的行为」一条用例。
