## 4. 残留 nit（不阻断合并）

1. **两条新路由没进 spec 的 API 契约**（建议合并前顺手补 3 行）。`GET /sessions/discover`、`POST /sessions` 目前只出现在证据与评审文档里，`docs/specs/2026-11-16-phase-0.5b-codex-pi.md` §6/§11 没有它们。0.5-C 要做「API v1 冻结」，这俩是要对外的门面，越早写进契约越省事。另外 `POST /sessions` 的返回从 `SessionRef` 变成了 `{session, created}`（`server.ts:416-419`）——同一 PR 内自洽，但如果 0.5-C 有外部消费者，需要在 spec 里明确这个形状。
2. **discover 路由没有默认 limit，且为每个发现结果都挂 pipeline**（`server.ts:344-372`）。本机 27 条无妨，但用户有上千 rollout 时会一次性 `registerDiscovered` + `attachPipeline` 上千条；而「发现到但没被控制面接管」的会话，driver 没有活通道，订阅是空转的（不产生事件）。建议给路由一个默认上限（如 100），或只对「本次 created 且随后被写入」的会话挂管线。
3. **`remember()` 是 FIFO 不是 LRU**（`discover/codex.ts:44-56`）：命中时 `cache.get()` 不刷新顺序，热文件在 4096 条之后仍会被淘汰。行为可接受（下限 4096 已足够），但注释/文档里写的是 LRU，建议改词或在 `get` 时一并 refresh。

## 8. 三轮评审的一条经验

这轮最值得记的不是那个 bug，而是它的**发现路径**：

1. 首评靠读代码怀疑 → S6 被「修」成 P0；
2. 复审靠**覆盖矩阵**（agent × 操作 × 入口）定位到空格 → 一个 5 行脚本实证；
3. 本轮修复既改了代码，也把那个空格变成了测试（`api-agents.test.ts:732`）。

矩阵化测试的价值在这里被验证了两次：一次是找到 bug，一次是防止它回来。Phase 0.5-C 做硬化时，建议直接把「3 agent × {inject, interrupt, resume, handoff, attach} × {API, driver 级}」做成表驱动用例，把这类空洞永久堵住。
