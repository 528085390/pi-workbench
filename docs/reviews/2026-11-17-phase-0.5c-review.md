## 1. P1：重启后「可接管」对所有 dispatch 出来的会话都不成立

规格 §7.1 写得很明确：「要写或续聊，先 `POST /sessions/:key/attach`（3s 超时）把 driver 接回来，成功后 status 置 `idle`。attach 失败返回 `E_RESUME_REJECTED` 或 `E_AGENT_UNAVAILABLE`」。实现与这句话不兼容：

- `server.ts:687-693` 用**会话自身声明的 caps** 判定，`attach !== true` 直接 422 `E_CAP_UNSUPPORTED`；
- `capabilities.ts:17-56`：Claude interactive / Codex / Pi 的 `attach` 全部 `false`，只有 `claude --bg` 后台会话是 `true`；
- 而 `takeover.ts:619` 里 dispatch 造出来的会话**一律 `kind: "interactive"`**，发现路径（`claude agents` 映射）在我读到的代码里也只产出 interactive/background 两种，后台会话需要用户自己在原生侧起。

结果是：杀 daemon → 重启 → 会话 `driver=none / status=unknown`（对账正确）→ 想接回来时 **没有任何一个端点能成功**。`handback` 是事实上的旁门（`takeover.ts:448-496` 只 `assertWriter` + `driver.resume`，不校验 status 是否 `handoff`），在"先 `POST /lease` 拿租约再 `POST /handback`"的组合下能跑通，但契约文档 §5 只写了"从人类手里接回"，e2e 也从未演练。

这不是实现失误，是被明确降级成"已知偏差"了：`scripts/e2e-restart.mjs:359-368` 把 422 作为**负向断言**保留，`restart-20261117-0352.md:31` 与 `:56` 都写了"attach 200 + inject-after-restart is not exercised"，`gate-summary` §已知偏差 1 也点了名。**披露是诚实的**，但代价是 C01 的四条硬指标里「可接管」只完成了 see：

| C01 要求 | 实际 |
|---|---|
| 未完成会话仍可见 | ✅ `sessions-count-unchanged`、`db-instances-2` |
| 可读 | ✅ `transcript-after-restart` 3 条消息 |
| 可接管（写/续聊） | ❌ 422；无替代端点 |

而 `docs/开发顺序与阶段门禁.md` 的 Gate 行已经打勾成「未完成会话不丢；可继续 see/resume」。

**建议（做在 Phase 1 之前，因为 v1 冻结后加路由要动契约+fixture）**：新增 `POST /api/cp/sessions/:key/resume`（语义：对 `driver=none && status=unknown` 的会话调 `driver.resume`，成功置 `idle`+`driver=pi`，失败 `409 E_RESUME_REJECTED`）。这正好是 v1 允许的 additive 变更，也把规格 §7.1 那句承诺兑现。若不愿加路由，至少把 `handback` 在 `status=unknown` 上的行为写进 `docs/api/cp-v1.md` 并加一条 e2e，别让它继续以"旁门"形态存在。

## 2. P2

### P2-1 operation-matrix 的 driver 半区是同义反复（C08）

`test/operation-matrix.test.ts:238-267`：`runDriverCell` 调的是 `makeDriver()` 造的脚本化 double，然后断言 `result.messageId === agent + "-m1"`、`box.calls` 等于 `[operation]` —— 这三件事全是 double 自己刚写进去的。30 个格子里 API 那 15 格是真断言（路由、能力闸门、成功形状、不调用 driver），driver 那 15 格对**真实 driver 零覆盖**。

`regression-20261117-0352.md:39` 写的是「逐一跑 API route 与 driver method」，字面没错，但读起来像三 Agent 的方法都被验证过。建议：把 driver 半区改成对 `ClaudeDriver/CodexDriver/PiDriver` 的能力矩阵断言（`capsOf(agent)` 与 `driver.caps` 一致、`attach=false` 的 agent 确实抛 `E_CAP_UNSUPPORTED`），或者直接在文档里写清「driver 列验的是控制面调用形状，真实 driver 由 e2e-three-agents 覆盖」。

### P2-2 C03「两次往返」没有真 Agent 证据

Gate 条目原文是「同一会话连续两次 handoff → native → resume，上下文仍然连续」。真实证据只有**一次**往返：`e2e-claude` 14 步（checkpoint → handoff → human-turn → handback，`handoff-roundtrip-20261117-0352.md:18-27`，人类回合 nonce 确实出现在 deltaSummary 里，这条是扎实的）。第二次往返只有 `takeover.test.ts` 的单测。`handoff-roundtrip.md:29-33` 把这件事分节写清楚了，属于诚实披露；但门禁文档与 `gate-summary` 的勾选读起来像"真实验证过两次"。

### P2-3 证据基线与 HEAD 不一致，且只补跑了一半

所有工件标注 `@ 769ede5`（`gate-summary` 头部、`restart-*.md:5` 等）。之后 `d023f07`（final review fixes）**改了行为**：`server.ts` 的 `/transcript` 增加 `pending` 字段、`/attach` 增加可用性前置、`/health.adapters` 改用探测缓存；`process-registry.ts` 的 POSIX 改为 `kill(-pid)`；`errors.ts` 增加 `E_ADAPTER_CRASHED`。

终审只复跑了 `cp test` / `ext test` / `e2e-restart`（`gate-summary` 末节）。`e2e-concurrency` / `e2e-faults` / `e2e-three-agents` / `e2e-claude` 四个工件**产出于改动之前**，其中 concurrency 与 faults 恰好会走到被改过的 `/transcript`（pending）与 `/health.adapters`（探测缓存）路径。建议：在 HEAD 上重跑这三个脚本；或在 gate-summary 明确写「其余三个脚本基于 769ede5，d023f07 未触及它们的断言路径」。这是"一键重跑 3 分钟" vs "下一轮无法复算"的取舍。

### P2-4 0.5-C 没有评审文档，review-fixes 记录也没进仓库

0.5-A / 0.5-B 都是 `docs/reviews/*-review-rN.md` + `docs/evidence/phase-0.5b/review-fixes-*.md` 成对出现，形成可复盘的闭环。0.5-C 有 `d023f07 (final review fixes)`（提交信息为空，只有这一句），`docs/reviews/` 下没有对应评审，`docs/evidence/phase-0.5c/` 下也没有修复清单。

### P2-5 handoff 的能力闸门在破坏性 close 之后

`takeover.ts:384-429`：先 `close`（不可逆），再 `#handoffCommand`；命令拼接阶段若抛 `E_CAP_UNSUPPORTED`（`takeover.ts:816-822` 的 attach 语义检查）走的是 `throw err`，"会话状态与租约不变"分支——但控制通道已经关了，库里仍是 `running` + 原租约，后续 inject 会打到已关闭的会话。

今天不可达（Codex/Pi 的 `handoff()` 只拼命令、不抛；Claude 走 `resume-tui`，不触发 attach 分支），但把 `driver.caps`/mode 判定提到 close 之前是零风险、一行成本的防回归。规格 §7.3 的补偿表也缺这一格（"capability 失败"没有对应行），建议一并补。

### P2-6（0.5-B 遗留，但会挡 Phase 1）列表接口的复杂度是 O(会话数 × transcript 大小)

`server.ts:317-330` 的 `viewOf` 为每个会话调 `readToEnd`（`limit=Infinity`）算 unread，即每次 `GET /api/cp/sessions` 都会把**每个会话的整篇 transcript 全量解析一遍**；`jsonl.ts:104` 的 `scanJsonl` 每次把「游标到文件末尾」整段读进内存。`GET /sessions` 是 Web 控制台必然轮询的主路由，20 个会话 × 几 MB transcript 就是每请求几百 MB 的解析量。

这一条**不是本分支引入**（`git show master:.../server.ts` 已有同样的 `readToEnd`/`viewOf`），C08 的约束也明确"不改解析语义"。我把它放在这里是因为 0.5-C 的目标就是"提升到可承载 Phase 1 Web 控制台"，而它恰好落在前端第一条要接的路由上。建议在 Phase 1 之前落一个 `unread` 的增量计数（EventStore 里有 seq 水位数，或用文件 size + 消息计数缓存），不要留到压力测试时才发现。

### P2-7 「同一 dispatch 只产生 1 个会话」这条 Gate 断言是空的

`scripts/e2e-concurrency.mjs:290`：

```js
record("dispatch-single-session", listed.sessions.filter((session) => session.key === key).length === 1, {...});
```

`sessions` 列表里同一个 key 不可能出现两次，所以左边恒为 `true`；真正的 `listed.sessions.length` 只被写进 detail，没有参与任何断言。如果并发回收窗口真的漏出了第二个会话（`takeover.ts:673` 的失败路径会把 adapter 会话关掉，但库里可能留一行不同 key 的僵尸），这条 check 依然 PASS。

实际挡住双会话的是另外两条真断言：`:288` 的三次响应 key 全等、`dispatch-single-row`（dispatches 表 1 行且 `status=done`）。所以证据存在，只是 Gate 原文「只产生 1 个会话」没有被直接断言。**建议改成断言 `listed.sessions.length === 1`**（或与 dispatch 前基线比较），一行的事。
