## 2. 新发现：P1（阻断）`POST /resume` 没有租约门禁

AGENTS.md 红线 3 原文：**「任何 inject / interrupt / handoff / resume 必须先持有租约；单会话单 driver。」** 新端点把 `resume` 这条漏了：

- 路由没有 `clientId` 入参、没有 `leases.assertWriter`，直接 `driver.resume(session)`（`server.ts:776-786`）；
- `docs/api/cp-v1.md` §4 的 resume 判定顺序写了 6 步，没有一步是租约；错误清单也没有 `E_NO_LEASE`；
- `e2e-restart.mjs` 的 resume 断言**不先取租约**就直接 POST，并成功拿到 200 —— 也就是说"无租约也能接管"已经被证据固化下来了。

因为租约判定被下沉到了各 driver 内部、而三个 driver 的实现不一致，同一个端点长出了三种行为：

| Agent | resume 时无人持租约 | resume 时**他人**持租约（含 human handoff） |
|---|---|---|
| claude | 200，且不留租约（`ClaudeDriver.resume` 无任何检查，`claude-driver.ts:50`） | **200** ← 危险 |
| codex | 200（`makeCodexWriteGuard` 放行空租约，`index.ts:72-83`） | 409 `E_LEASE_CONFLICT` ✅ |
| pi | 200，但 `#claim` 会把租约**抢过去**记在内部 `pi` 客户端名下（`pi-driver.ts:381-385`） | 409 `E_LEASE_CONFLICT` ✅ |

两个具体后果，都不是理论问题：

1. **claude 会话 resume 到人类手里时没有任何阻拦。** human handoff 的会话 `driver="human"`、status `handoff`、租约在 `handoff-<pi>` 名下；`caps.resume` 为 true、路由不看 status 也不看租约 → 直接 `adapter.resume(nativeId, cwd)` 发一条 ACP `session/resume`。这正是 `#closeDriverRef` 与 Pi `handoff` 花力气避免的事（`takeover.ts:766`、`pi-driver.ts:220` 的注释：A11 实测原生会话无文件锁，daemon 与人类终端会同时写同一个 jsonl）。
2. **Pi 会话 resume 之后紧接着 inject 会 409。** `#claim` 把租约写成 `{clientId:"pi"}`、有效期取 `LeaseManager` 默认 30s，而这条路径不经过引擎的 `#driverWrite` 换租约/还原逻辑，没人释放它；调用方（自己的 clientId）接着 `POST inject` → `assertWriter` → `E_NO_LEASE`，最长等 30s 才恢复。也就是说「接管成功了但立刻用不了」，而 Gate 要证明的恰恰是"能继续用"。

**建议**（与既有结构一致，改动面很小）：把 resume 的语义下沉到 `TakeoverEngine`（照 `handback` 的形状：`assertWriter` → `#driverWrite` → `driver.resume` → 注册表/事件），路由只保留"存在性 + 可用性 + caps"三道闸并接收 `clientId`。这样三个 Agent 行为一致、Pi 的租约不会悬着、claude 也受红线 3 约束。另外建议拒绝对 `driver="human"` / `status ∈ {running, starting, handoff}` 的会话 resume（文档里补一条错误码，`409` 即可），并在契约里补 `409 E_NO_LEASE`。

## 3. P2

### P2-8 resume 的正向证据停在"状态翻转"，没证明"接管后能用"

`e2e-restart.mjs:371-383` 断到 `driver=pi / status=idle` 就结束了。规格 §7.1 的验收原话是「attach 后可 inject」，而这条新链路的用户可见价值就是"接回来还能继续聊"。
补一步即可：`POST /lease`（取租约）→ `POST /inject` → 断言消息回显到 transcript。**这一步恰好会把 §2 的租约问题当场暴露出来**（claude 漏检查、Pi 悬租约），所以我建议它和 §2 一起改。

### P2-9 codex / pi 的 resume 路径零覆盖

`api.test.ts` 的 5 条 resume 用例用的都是同一个脚本化 claude driver double，`operation-matrix` 的 resume 格也是 double。于是 §2 表格里 codex/pi 的两行行为（我读代码得出的 409 / 悬租约）没有任何测试固定下来，改 driver 内部实现就会静默漂移。建议：至少给 pi 加一条"resume 后调用方 inject 不 409"的用例（用 `operation-matrix` 的 harness 就能写）。

### P2-10（残留）`e2e-three-agents` / `e2e-claude` 仍未在 HEAD 复跑

这两个脚本覆盖的是三 Agent 的 dispatch/inject/handoff 主链路，而 `d023f07`+`4b42e4e` 改过 `/transcript`（新增 pending）、`/health`（非阻塞 + 探测缓存）与 `killAll`。改动本身是 additive/内部实现，风险低，md 也披露了基线，所以我不再算阻断；但"三 Agent 回归在 HEAD 通过"这句话目前严格说只对 concurrency/faults 成立。跑一次约 1 分钟收掉最干净。
