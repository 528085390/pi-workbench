## 3. P2-1 的新缓存逻辑没有测试

`refreshTranscriptPath` 这次长出了三件新东西，全是「时间 + 并发」语义，也正是最容易回归的一类：

1. single-flight：列表与通知器同时触发时只解析一次；
2. 30s 负缓存：解析失败的会话在窗口内不再扫；
3. `running`/`starting` 不缓存 miss：避免新 rollout 刚创建就被判死。

现有测试只覆盖了「happy path 通过 HTTP 补出 transcriptPath」（上一轮就有）。建议补 3 条（都在 takeover 或 api-agents 层可写）：

- 同一 key 并发调两次 `refreshTranscriptPath` → driver 的 `resolveTranscriptPath` 只被调用 1 次；
- 状态 idle 的会话解析失败后，30s 内再调 → 不再调用 driver；注入时钟快进 31s → 重新调用；
- 状态 running 的会话解析失败后立刻再调 → 仍会重试（不缓存）。

这条留给你的判断：它不影响功能正确性，但「新逻辑零测试」正是前几轮反复出现的问题模式。可以随 0.5-C 一起补，前提是**落进任务表**，别只留在证据文档里。
