行号碰巧还落在同类行上（因为脚本行结构稳定），所以不细读不会发现；但「证据可复核」是这个阶段的立身之本，第三次栽在同一类问题上（r1 门禁未勾选 → r2 自述不符 → r3 引用漂移）。建议任选其一根治：① 证据文件按 run 命名（`e2e-61080ebe.jsonl`）并在文档里指文件名而非行号；② 门禁文档不再抄具体数值，只写「见 jsonl 中 `step=discover` 行」；③ 由脚本生成门禁表格。

### P1-2（必修，回归）Claude 的严格回归证据早于本轮的 Claude adapter 改动

本轮的 `3a68ffa` 改了 `claude.ts`（`#applyInitialPermissionMode` 在**每次** `newSession` / `resume` 后多发一条 ACP 请求）、`cf9a4cc` 改了 spawn 选项、`67bddbc` 给所有 update 加了 `sessionId`——都直接落在 0.5-A 的核心路径上。但 `claude-regression-run1/2.jsonl` 最后一次更新是上一轮的 `5f8243a`（09:46 那次），**早于本轮代码**；门禁文档 §3 也仍引用 09:46 的 run id。

部分代偿：本轮 15:19 的 E2E 里 Claude 走了 dispatch→see→inject→interrupt→checkpoint→handoff→human-turn→handback 全链路并通过。但「Gate #1 = 严格版 e2e 两轮 PASS」这条结论，形式上仍应由改动后的代码重跑两轮来支撑。建议补跑一次（`scripts/e2e-claude.mjs` 连跑两次，约 2 分钟），或把 Gate #1 的证据改成「E2E + 回归两份，回归标注对应的 commit」。**顺带确认一件事**：`#applyInitialPermissionMode` 让每个新会话多一次 ACP 往返，请确认真机上 session 建立耗时没有明显回归（E2E 里没测这一段）。

### P2-1（性能）`/sessions?clientId=…` 会对每个未解析路径的会话各触发一次发现扫描

`server.ts:406-412` 列表接口对每条会话调 `ensureTranscriptPath` → `engine.refreshTranscriptPath` → driver 的 `resolveTranscriptPath` → Codex 走 `#discoverRolloutPath`（一次完整 `discover`，`limit:1000`）。没有负缓存：解析不到就每次调用都重扫。

读路径本来就是这么做的，但现在挂到了**列表**上，而列表是 `TurnNotifier` 每次回合结束都会拉两次（`refreshBadge` × 2）。多会话 + 一条永久解析不出来的 codex 会话时，这会变成「每个通知周期若干次目录扫描」。目前有 LRU 首行缓存兜着（实测 1000 文件 19ms），所以不致命，但建议：① 对「解析不到」做 30–60s 的负缓存；② 或只在 `unread>0` 且确实需要时解析。

### P2-2（语义）`resume` 也会重置权限模式 → handback 会覆盖人类在接管期间改的模式

`claude.ts:186,197`：`newSession` 与 **`resume`** 都会 `#applyInitialPermissionMode`。于是「handoff 给人类 → 人类在原生 TUI 里把权限改成 plan/只读 → handback 接回」这条链上，daemon 会把模式硬改回 `config.claude.initialPermissionMode`（本机是 `bypassPermissions`）。Codex 同理（`INITIAL_AGENT_MODE` 在 resume 后仍由 adapter 侧生效）。

这未必是错的（引擎认为配置是真相），但它是一个**人类可感知且安全相关**的副作用，且当前没有任何日志。建议：handback 路径要么不重置（只在 newSession 时设），要么在 `state_update`/`notice` 里记一条「权限模式已重置为 X」，让接管的人知道。

### P2-3（工程）`pi-workbench.plugin.ts` 零类型检查、零测试

`packages/extension/tsconfig.json` 的 `include` 只有 `src/**/*.ts`，而插件入口在包根（`pi-workbench.plugin.ts`，因为它 `import from "./dist/index.js"`）。结果是：**本轮改动最关键的宿主逻辑（会话 key 识别、通知器生命周期、工具名传递）既不过 `pnpm -r build`，也没有任何测试能覆盖**——类型错误只会在用户装插件时以运行时错误暴露。

本轮它的改动恰好不小（`startNotifier` 抽取、`currentSessionKey`、`excludeSessionKeys`、`wrapToolExecute(…, name)`）。建议加一个 `tsconfig.plugin.json`（`rootDir: "."`, `include: ["pi-workbench.plugin.ts", "src/**/*.ts"]`）并纳入 `pnpm typecheck`；有精力再补一个用假 `ExtensionAPI` 的冒烟测试（session_start → 建 notifier → session_shutdown → 释放）。

### P3-1（一致性）Codex 的 `initialPermissionMode` 硬编码 `"auto"`

`codex-acp.ts:41` 固定 `initialPermissionMode: "auto"`，而 Claude 侧是 `config.claude.initialPermissionMode`。两者是同一个 ACP 概念（`set_config_option(mode)`），一个可配一个写死。虽然 Codex 的沙箱强度主要由 `INITIAL_AGENT_MODE` 决定，但读代码的人会困惑。建议加一行注释说明「Codex 的 mode 不是用户级开关，沙箱由 initialAgentMode 控制」，或干脆复用配置。

### P3-2（脆弱点）`child-process.ts` 的全局 patch 依赖调用时序

`hideWindowsChildProcesses()` 用 `syncBuiltinESMExports()` 改全局 `spawn`，只对**之后**才解析的模块生效（Pi 包是动态 import，所以有效；`claude.ts` 是静态 import，所以另加了显式 `windowsHide`）。这个「静态 import 走显式参数、动态 import 走全局 patch」的分工是对的，但没有写在任何地方，未来有人删掉 `claude.ts` 里的 `windowsHide` 或把 Pi 包改成静态 import，就会静默退回弹窗。建议在 `child-process.ts` 头注释里加这两句，并在 `claude.ts` 那处注释里回指。

### P3-3（极轻）`consecutiveWakes` getter 有副作用

`notify.ts:145-148` 的 getter 里调 `#resetWakeBudgetIfStale()`，即读一次诊断值就重置计数器。功能上无害（本来就是时间窗语义），但 getter 改状态容易在后续重构里咬人。建议改成 `wakesInWindow()` 之类的方法名，或在注释里点明。

## 5. 亮点（这轮最值得学的部分）

1. **正反馈闭环的根因拆到四条，每条都对上了代码**。`notification-self-loop.md` 把「Pi 收到自己的通知 → 调 cp_sessions/cp_see → 读取自己写回 jsonl → 产生新未读 → 再通知」这条环拆成：受控子进程加载了宿主插件（`#extensionRpcArgs`）、自身会话未排除（`excludeSessionKeys`）、观察型工具重置了连击上限（`noteToolActivity` 认工具名）、seq 无去重 + 计数无窗口（`#lastEventSeq` + `wakeWindowMs`）。四条修完还留了「子 Pi 默认 `--no-extensions`」的物理隔离——**双层防御，不是压症状**。
2. **顺手补掉了 0.5-A 就存在的跨会话事件串写**。`pipeline.ts:201` 按 `update.sessionId` 过滤，配合 `AdapterUpdate.sessionId`、`claude.ts` 的三处 emit、`pi-driver.ts:353` 的伪 ref 改写。这是「一个 adapter 进程服务多会话」这个设计一直没付的账，早该有人付。
3. **懒解析从 driver 内存上提到了注册表**（`takeover.ts:205`）：这修的不是一个 404，而是「事件能收到但 unread 恒 0，于是通知被规则 1 丢掉」这种**静默失效**——最难查的一类。
4. **权限模式显式化**：不依赖 `settings.json`（会被 `filterEscalatingDefaultMode` 降级），直接发 `set_config_option`，并在证据里写清 Codex 各模式的实际含义（`agent-full-access` = `approvalPolicy:never` + `dangerFullAccess`）。诚实、可复核。

## 6. 一条安全提示（不阻断，但请在文档里显式化）

`agent-permission-modes.md` 记录本机 `config.yaml` 已设为 `claude.initialPermissionMode: bypassPermissions`、`codex.initialAgentMode: agent-full-access`，即**两个 Agent 都跑在「全权限、不审批」**。默认值仍是较安全的 `auto` / `workspace-write`，这点做得对。

但这是 daemon 的全局配置，未来接 Web UI/多客户端时，「谁都能在这个全权限 daemon 上 dispatch」等于「谁都能以你的身份全盘读写」。建议：① daemon 启动时打一行 `[pi-workbenchd] claude=bypassPermissions codex=agent-full-access（无沙箱）`；② `GET /agents` 把生效的权限模式作为字段返回（UI 才能显示「本会话无沙箱」）；③ 在 PRD 的风险表里记一条。现在是 0.5-C 之前最合适的时点。
